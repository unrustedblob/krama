**Title:** `r001 · 1: Python version check — minimum and comparison`

````markdown
From review r001 (`docs/review/m1/cli-args/r001.md`), `tests/harness/kramat.py`, module top.

- [ ] **1.1 — Minimum is still 3.11.** The minimum Python version moves to **3.13** (new decision,

  follow it. The f-strings that need PEP 701 (3.12+) stay as they are.
- [ ] **1.2 — Version strings compared as text.** `"3.9.1" < "3.11"` is `False` (`'9' > '1'`), so
````

### Issue 2

**Title:** `r001 · 2: parse_c_int misreads C integer literals`

````markdown
From review r001 (`docs/review/m1/cli-args/r001.md`), `tests/harness/kramat.py`, `parse_c_int`.

The self-check passes today only because the header's explicit values (`0`, `2`) are single digits.

- [ ] **2.1 — Digit order reversed.** `enumerate` weights the *first* character with `base**0`, so
  `"23"` reads as 32. Use Horner's method: left to right, `value = value * base + digit`.
- [ ] **2.2 — Hex with a leading zero digit becomes octal.** The prefix checks are not one chain:
  `0x0F` strips to `0F`, which then matches the octal branch.
- [ ] **2.3 — Invalid characters ignored.** `3u`, `(1<<3)`, `019` (octal), `0b12` all return a
  number. The docstring promises `None` on error: any character that is not a valid digit for the
  base must return `None`.
- [ ] **2.7 — A first implicit enumerator gets 1, not 0.** In `extract_exit_codes`, `latest = 0`
  followed by `latest + 1` gives an implicit *first* enumerator the value 1; C gives it 0. Track the
  *next* value instead: start at 0, assign, then increment. Hidden today because `SUCCESS` is
  explicit.

**Expected results** — use asymmetric inputs; palindromes and single digits cannot detect 2.1:

| Input | Today | Expected |
|---|---|---|
| `"12"` | 21 | 12 |
| `"023"` | 26 | 19 |
| `"0x0F"` | `None` | 15 |
| `"0b101"` | 5 (by luck) | 5 |
| `"1'000"` | 1 | 1000 |
| `"3u"` | 3 | `None` |

**Out of scope:** 2.4–2.6 (no enum scoping, no unknown-line rule, trailing comments) are deliberate —
the cross-check against the planned `--dump-exit-codes` flag covers them.

**Done when:** every row above returns its expected value, and a header whose first enumerator is
implicit maps it to 0.
````

### Issue 3

**Title:** `r001 · 3: Manifest validation drifts from the contract`

````markdown
From review r001 (`docs/review/m1/cli-args/r001.md`), `tests/harness/kramat.py`,
`validate_case` and `load_stage_manifest`. Contract: krama-notes-18 §2, §7; krama-notes-20 App. A.2.

- [ ] **3.1 — Unknown keys accepted.** Only missing keys are checked. The key set must *equal*
  `{name, args, return_code, stderr, expected}`, so `timeout = 5` must be a manifest error (M7).
- [ ] **3.2 — List elements not checked to be tables.** `case = [1, 2]` crashes in `case.get` with a
  traceback instead of a manifest error (M6).
- [ ] **3.3 — `#derive` stricter than decided.** The code requires `args` to be *only* the `.krm`;
  the contract says exactly one argument ending `.krm` *among* the arguments (M10). Either align the
  code or record the narrower rule.
- [ ] **3.4 — `case = []` passes.** Zero cases is an empty manifest (M4).

**Done when:** each case above produces a `ManifestError` naming the problem, or 3.3's narrower rule
is recorded.
````
